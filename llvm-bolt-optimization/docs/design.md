# 设计说明

## 问题与已有实现

LLVM BOLT 已有 `hfsort` 和 `cdsort`，因此“把高频调用的函数靠近”不是本项目的新贡献。
HFSort 已检查调用概率、聚类大小与热度密度；CDSort 已综合函数大小、调用权重与调用偏移。
本项目在现有结果上增加**小函数范围内的受限局部交换与全图距离收益检查**，不替换现有布局框架。

代码依据（均为 `LLVM_REVISION` 中固定的提交）：

- `bolt/lib/Passes/ReorderFunctions.cpp`：命令行选项、调用图构建、函数索引排序。
- `bolt/lib/Passes/HFSort.cpp`：HFSort 现有聚类及合并约束。
- `llvm/lib/Transforms/Utils/CodeLayout.cpp`：CDSort。
- `bolt/lib/Core/BinaryFunctionCallGraph.cpp`：profile 调用图与调用偏移。
- `bolt/lib/Rewrite/BinaryPassManager.cpp`：重排后使用 `PopulateOutputFunctions` 产生输出顺序。

创新范围仅针对本次检查的这些路径；不声称提出了新的通用布局算法，也不声称穷尽了所有相关研究。

## 实现

排序逻辑集中在 `ReorderFunctions.cpp`，默认关闭的新选项为 `--small-function-layout`。
`BinaryFunction.h` 仅增加一个交换两个有效索引的方法，保留原有 `setIndex()` 只能首次赋值的约束；另外添加一个汇编回归测试。
先运行现有排序，再按现有比较函数取得基线顺序，在最终输出顺序产生之前交换函数索引。
新步骤重新调用 `buildCallGraph`，避免使用已被 CDSort 调整过的边权重；不启用陈旧 profile 回退。

候选函数必须：

- 有有效 profile、有效排序索引和至少 100 次执行计数，排除仅执行一次的启动代码及低计数函数。
- 是可处理的简单 CFG 函数，非忽略函数、PLT 函数、分裂函数。
- BOLT 估计代码大小为 1–128 字节，且没有显式前后 padding。
- 至少具有一条正权重的有效调用边。

只交换顺序中相邻且同时合格的函数，所以其他函数构成区间边界，位置索引保持基线结果。
`none`、`exec-count`、`hfsort`、`cdsort`、`pettis-hansen` 可作为基线。
无重定位信息、用户顺序文件、`user`、`random`、`hot-functions-at-end` 或存在特殊 hot-text mover 函数时跳过。
普通重排自动开启的 `hot-text` 不阻止本优化；只有 mover 导致后续顺序分区时才跳过。

定义模型：

```text
address(f) = 按当前函数顺序累加 max(estimateSize(f), 1)
D = Σ weight(u,v) × |address(u) + avgCallOffset(u,v) - address(v)|
```

模型包括筛选后的调用图中全部正权重非自递归边，包括大函数与区间外函数的调用边。
有效 profile 和已知目标仍不能恢复采样中未出现的调用；“全图”指可构建的有效 profile 调用图。
调用图对同一函数对的调用点聚合并使用平均偏移，这是 BOLT 既有表示带来的近似。

交换 A、B 时，两者估计总大小不变，后续函数的模型地址不变。
因此只需重算所有与 A 或 B 相连的入边、出边，对 A↔B 的共享边去重。
收益不严格为正则恢复地址且不修改索引。使用 `long double` 计算，并设置相对 `1e-12` 的接受容差。
最多扫描 64 轮，某轮无交换则提前终止。遍历及平局处理确定，不引入随机性。
原有聚类统计在局部修正之前输出；新步骤应使用 `small-function-layout` 的距离日志及生成的最终顺序来评估。

复杂度：调用图和邻接表占 O(V+E) 空间；每轮候选交换按受影响节点度数计算，不对每一对重新扫描全图。
固定 64 轮限制了搜索成本，但可能停在局部最优之前。

## 正确性与验证

新步骤只交换索引，复用 BOLT 的代码重定位、分支修正与输出流程。
阈值和 profile 条件限制优化范围；不合格函数保持其基线索引，而非承诺字节地址不变。
接受条件只保证上述估计指标单调下降，不能从数学上保证实际执行时间不回退。

回归用例包含：

1. A、B 为相邻小函数，main、C 超过阈值。
2. A→C 距离可因交换变短，同时 main→A 可能变长。
3. 调整 main→A 的 profile 权重，分别验证接受、平局拒绝、外部边否决。
4. 用户顺序文件保持原样。
5. 三种负载的多组输入校验和一致；无 profile 跳过；默认关闭结果与显式关闭的顺序一致。

测试中的人工权重仅用于确定性回归，不用于性能结论。
性能实验使用执行生成程序获得的真实 BOLT 插桩 profile。

## 实验方法

- `correlated`：64 组、每组 32 个小函数，组内形成频繁执行的调用链，定义顺序固定打乱。
- `dispersed`：512 个小叶函数，由大 dispatch 函数以确定性伪随机输入分散调用。
- `ordinary`：对 128 元素数组反复更新，函数数量少且核心函数较大。
- GCC `-O2`，关闭内联、同函数折叠和尾调用优化，保留静态重定位；程序结果被打印以防死代码消除。
- 训练与计时运行分开；原始程序、BOLT 关闭/开启，以及 CDSort 关闭/开启使用同一输入。
- 固定一个允许的逻辑 CPU，预热，按固定随机种子交错运行 15 次，记录 wall time 中位数及 min/max。
- 同一程序的所有模式采用相同计时迭代数；不同程序分别校准迭代数。
- 记录文件大小、objdump 标为 CODE 的段大小总和、GNU size 的 text 大小、交换次数、内部估计距离，并使用输出符号地址估算可解析 profile 边距离。
- GNU size 的 text 包含只读数据等分配段，不等同于纯机器指令字节数；文件大小受调试信息、重定位和元数据影响。
- `weighted_distance_profile_offsets` 使用输入 profile 的调用偏移与输出符号地址，不代表精确输出调用点距离。

实测结果见 `../results/RESULTS.md`、`summary.json` 和 `timings.csv`。不根据人工回归权重生成性能数据。

## 本次实测结论（2026-11-11）

最终版本将扫描上限从 8 提高为 64，仍只接受加权调用距离严格下降的相邻交换，没有引入新算法或额外优化选项。
较低上限过早限制了搜索；关联负载的交换数从 13967 增至 42935，距离减少从约 1.97% 增至约 6.65%。
超过上限仍可能有更好排列，本项目没有搜索最优布局。

Ubuntu 24.04 / WSL2、GCC 13.3、Release 且启用断言的 BOLT 完成编译及全部功能验证；容器内同样通过回归与 48 组输出对照。

## 验证结论：最终 64 轮版本

本轮完整对照为三类程序、五种模式、各 31 次，共 465 次计时；另用运行顺序种子 456，对关联负载独立重跑 31 轮五种模式，共 155 次。
第一次实验的配对改善中位数为 2.44%，探索性 bootstrap 95% 百分位区间为 1.88%–3.13%；独立确认约为 2.63%，区间为 1.21%–4.31%。
这两次测量支持本机所测关联小函数负载相对 exec-count 基线有收益；不表示所有工作负载或机器都加速。

分散调用的配对区间跨越零，未确认收益。普通程序零交换，代码段完全相同，时间差属于噪声，不能归因于本优化。
关联负载在 CDSort 基线上零交换，未确认额外收益。所有开启/关闭对照的 CODE 段大小相同，没有代码体积收益。
两组独立中位数的百分比与“按重复轮次配对”的改善中位数是不同估计量，不应混用；原始 CSV 和 uncertainty.json 均已保留。

bootstrap 依赖重复块相互独立的假设。首轮候选实验期间存在 Docker 准备活动，因此另做了无并行构建、不同顺序种子的确认实验。
未采集硬件 I-Cache miss，不能据此声称缓存未命中已被直接测量。
原 8 轮实现的点估计及其跨零区间作为负面结果保留，没有删除或替换为成功数据。

Docker 不足通过独立的离线运行镜像路线解决：官方 Ubuntu 基础镜像经 SHA256 校验后本地加载，已安装的工具链从宿主机打包进镜像。
断网构建和断网容器测试均通过。完整源码编译已经在 WSL 中验证；不声称在容器内重新编译了整个 LLVM。

## 局限

只考虑相邻交换，不能跨越大函数或不合格函数，64 轮也不保证找到最优调用簇；提高上限增加离线优化开销，本次未单独量化该开销。
已被 CDSort 充分优化的程序可能没有可接受交换；工作集能放入 I-Cache 的程序可能没有可测收益。
分散调用可能被分支预测、数据依赖等瓶颈主导；布局模型改善不必然改善执行时间。
模型忽略最终对齐、指令编码变化和外部函数热冷分裂后的实际摆放，也不直接模拟缓存组冲突或返回路径。
执行计数阈值是简单的保守筛选，不是统计置信度保证；训练时长或采样量变化会影响候选集。
没有跨机器实测之前不能推广结果；WSL 的虚拟化与 CPU 频率变化会影响计时。
缺少有效数据时跳过可以避免本步骤改变布局，但不能保证其他 BOLT 处理无性能变化。
